# 设计技术与中英文排版规范

> 版本：v1.2｜更新日期：2026-09-12  
> 用途：产品设计、UI/UX、运营视觉、技术文档、产品文案及中英文混排内容的设计、评审与交付检查。

## 1. 适用范围

本规范是一套独立的设计与排版知识体系，覆盖：

1. 视觉设计基础：对齐、分组、对比与一致性
2. 产品与交互：反馈、预防错误、信息层级与帮助机制
3. 色彩与字体：色彩关系、字体分类、组合与可读性
4. 文案与排版：中文、西文、中西文混排及常见格式
5. 设计协作：职能边界、评审方法与交付检查

规范适用于界面、网页、移动应用、活动视觉、海报、Markdown、技术文档和一般产品文案。具体产品已有明确品牌或设计系统规则时，以其正式规则为优先。

## 2. 规范层级与裁决顺序

用户明确的体例、修改范围和原文保真要求优先。论文及专业文本的语言润色必须先读取并使用 [academic-humanizer](../../academic-humanizer/SKILL.md)；本文只保留排版、正式名称和实际格式接口要求，不另设正文文风。其余排版冲突按以下顺序判断：

1. **官方写法优先**：品牌、产品、应用、技术名词以其官方网站或官方商店中的写法为准。
2. **语言环境优先**：中文句子使用中文排版规则；完整英文句子使用英文排版规则。
3. **语义与可读性优先**：避免为了形式一致而降低理解效率。
4. **同一作品一致优先**：同层级、同场景、同组件应保持统一。
5. **具体场景优先于通用规则**：例如 `%`、`°`、`4K`、`1080p` 等特殊写法优先于“数字与单位之间加空格”的通则。

本文中的“必须”“不要”表示强制规则；“建议”“优先”表示推荐做法或经冲突归并后的执行建议。

## 3. 设计基础原则

### 3.1 对齐 Alignment

- 页面元素不得随意摆放，每个元素都应与其他元素建立明确的视觉联系。
- 优先建立可感知的对齐线，例如左边缘、右边缘、文字基线、内容中心线或网格线。
- 即使元素物理距离较远，也应通过对齐建立关联。
- 一个成熟页面即使视觉丰富，也应能找到稳定的对齐依据。

**检查要点**

- 同级标题、正文、按钮和表单控件是否共享稳定的对齐线。
- 相邻模块的边缘、基线和内容起点是否无意错位。
- 是否为了局部效果破坏了全局网格。

### 3.2 归类与分组 Proximity & Grouping

- 相关信息应靠近并组成视觉单元。
- 不相关的信息应通过距离、分隔、背景、标题或容器建立区分。
- 分组的目标是降低混乱、建立结构、提高记忆与扫读效率。
- 分组后形成的留白也应有规律，不应只是“空出来”。

**检查要点**

- 用户能否快速判断哪些信息属于同一组。
- 组内间距是否小于组间间距。
- 是否存在依赖边框才能勉强区分的弱分组。
- 是否因分组过多造成容器嵌套和视觉噪声。

### 3.3 对比 Contrast

- 不要让需要区分的元素“差一点点”；如果功能、层级或状态不同，应让差异足够明确。
- 可通过字体、字号、字重、颜色、大小、线宽、形状和空间关系建立对比。
- 对比有两个目标：
  - 增强页面吸引力与可读性。
  - 表达信息层级与逻辑流程。
- 对比不得误导用户，也不得错误强调非重点信息。

**检查要点**

- 第一眼能否识别页面重点和主要动作。
- 主次信息的差异是否足够明显。
- 是否出现多个元素同时争夺注意力。
- 状态差异是否只依赖轻微颜色变化。

### 3.4 重复与一致性 Repetition & Consistency

- 通过重复统一的视觉元素连接页面或多页作品。
- 可重复的要素包括颜色、形状、材质、间距、线宽、字体、字号、图片风格和交互模式。
- 同一用语、功能与操作应保持一致。
- 一致性不仅是外观统一，也包括行为、流程和反馈统一。
- 一致性的目标是建立秩序、连续性、品牌感和信赖感。

**检查要点**

- 同一层级是否使用同一字号、字重和间距。
- 同类组件是否有相同的状态、行为和反馈。
- 同一概念是否使用多个名称。
- 跨页面是否存在不必要的样式或操作差异。

## 4. 产品与交互设计原则

### 4.1 及时反馈

- 系统应让用户知道当前状态。
- 用户操作后应及时提供与动作相对应的反馈。
- 反馈应说明发生了什么、是否成功、是否仍在处理中，以及下一步是什么。

### 4.2 贴近现实

- 使用用户熟悉的语言、词语和概念，避免暴露内部系统术语。
- 信息结构和操作顺序应符合现实世界惯例与自然思考逻辑。

### 4.3 系统一致

- 同一用语、功能和操作方式保持一致。
- 组件、流程和反馈应遵循统一设计体系。

### 4.4 预防错误

- 优先通过设计防止错误，而不是在错误发生后仅显示提示。
- 在用户执行动作前，应减少容易混淆或误选的选项。
- 对高风险动作，应强化目标、影响和确认信息。

### 4.5 遵从习惯，降低记忆负担

- 让动作与选项可见，减少用户回忆信息的负担。
- 流程名称应真实描述下一步结果，避免含糊或跳步。
- 操作顺序应符合用户预期。

### 4.6 突出重点

- 用户通常是在“扫”界面，不是在逐字阅读。
- 应突出关键内容、弱化次要内容、删除无关信息。
- 重要对话或关键流程中不得混入无关内容。

### 4.7 错误帮助与恢复

- 错误信息应使用自然语言，不应只显示 `404` 等错误代码。
- 错误信息应准确说明问题、影响和解决方式。
- 设计应帮助用户恢复，并尽量降低损失。

### 4.8 人性化帮助

帮助方式从优到次为：

1. 设计足够清晰，无需提示
2. 一次性提示
3. 常驻提示
4. 帮助文档

帮助内容应与当前任务相关、容易找到、步骤明确。

## 5. 设计价值观

### 5.1 清晰

- 减少不确定因素和用户判断次数。
- 明确信息层级与操作导向。
- 流程直观、表意明确、组件简洁。
- 让用户在短时间内理解并作出判断。

### 5.2 一致

- 样式规范、操作流程和呈现方式保持一致。
- 从通用场景中抽象组件，形成可复用标准。
- 一致性用于提升效率、品牌感与信赖感。

### 5.3 韵律

- 通过有规律的间距、重复、模块组织和操作节奏建立韵律。
- 信息模块应排布匀称，元素应按功能和内容属性形成有规律的重复。
- 韵律应符合用户习惯，减少理解与记忆负担。

### 5.4 包容、开放与灵活

- 通用组件无法覆盖所有复杂业务场景。
- 在设计原则和体系边界内，应允许基于功能与场景调整样式、模型和交互形式。
- 灵活不是任意变化；调整仍应保持清晰、一致和可复用。

## 6. 色彩技术

### 6.1 色环基础

- 色环是配色的基础工具。
- 三原色为黄、红、蓝，不能由其他颜色混合得到。
- 相邻原色等量混合得到三间色：
  - 黄 + 蓝 = 绿
  - 蓝 + 红 = 紫
  - 红 + 黄 = 橙
- 继续混合相邻颜色可得到第三色，形成更完整的色环。

### 6.2 互补色

- 色环上相对的颜色互为互补色。
- 互补色对比强烈，适合“一种作主色，另一种作强调色”。
- 不建议让两种互补色以相同面积和强度竞争。

### 6.3 三色组

- 色环上彼此等距的三种颜色可形成协调的三色组。
- 红、黄、蓝是常见的基色三色组，常见于儿童产品。
- 三色组应通过主次和面积分配建立层级。

### 6.4 色调、暗色与亮色

- 纯色为色调。
- 色调加入黑色形成暗色。
- 色调加入白色形成亮色。
- 可用同一色调的明暗变化建立层级和状态，保持视觉统一。

### 6.5 暖色与冷色

- 含红或黄倾向的颜色通常为暖色；含蓝倾向的颜色通常为冷色。
- 暖色具有趋进性，更容易吸引注意，适合激活区域和重点信息。
- 冷色具有后退感，更适合背景、导航和低关注信息。
- 可通过加入红、黄“加热”颜色，或加入蓝“降温”颜色。

### 6.6 色彩使用原则

- 颜色应服务于信息层级和状态，不只是装饰。
- 强调色应克制使用，避免多个高饱和颜色同时争夺注意力。
- 主色、辅助色、强调色和状态色应保持稳定角色。
- 色彩与对比、字号、字重和空间共同表达层级，不能只靠颜色。

> 本规范未规定具体色值、色板数量、无障碍对比度阈值、深色模式算法和 Design Token 命名；这些内容需在具体产品规范中补充。

## 7. 字体与字体组合

### 7.1 六类字体

| 类别 | 主要特征 | 适用建议 |
|---|---|---|
| 旧式体 Oldstyle | 有衬线；斜向强调线；粗细变化自然 | 干扰少、正文可读性好，适合长文 |
| 现代体 Modern | 水平细衬线；垂直强调线；粗细反差强 | 醒目、高雅，适合大字号展示；不宜大段正文 |
| 粗衬线体 Slab serif | 粗衬线；粗细差异小或没有 | 直接、厚重、可读，适合强调或特定长文场景 |
| 无衬线体 Sans serif | 无衬线；笔画粗细通常较均一 | 简洁、现代，适合界面和信息展示 |
| 手写体 Script | 模拟书法笔或钢笔手写 | 用于风格化表达，不宜承担大段正文 |
| 花体 Decorative | 装饰性强、情绪鲜明 | 用于短标题或特殊场景，避免影响识别 |

### 7.2 字体组合

- 组合字体时应形成明确差异，不要选择结构过于接近、却又不完全相同的字体。
- 可通过不同字体结构建立对比。
- 衬线体与无衬线体的组合是常见且稳定的方法。
- 字体组合应服务于层级，不应只为展示字体数量。
- 同一层级的字体和字号必须一致，避免复制粘贴造成的样式漂移。

### 7.3 大小写

- 尽量不要使用全大写长文本。
- 全大写单词整体轮廓相近，会降低识别性和可读性。
- 如果全大写对短标题或视觉表达的收益明显，可谨慎使用。
- 正文、按钮和长标签优先使用自然大小写。

> 本规范未规定中文字体家族、字号阶梯、字重阶梯、行高、字距或跨平台回退字体；具体产品应另行定义 Typography Token。

## 8. 文案风格

### 8.1 准确与精练

论文及专业文本的语言润色按 [academic-humanizer](../../academic-humanizer/SKILL.md) 执行。排版检查核对错别字和误改的术语；不得删去条件、必要背景、证据冲突或操作步骤。只检查受改动影响的内容与呈现，不固定全文复核次数，严禁例行计算文本或备份哈希。

### 8.2 使用用户语言

- 使用用户熟悉的概念，不使用内部系统术语。
- 产品状态、错误和操作结果应直白、准确。
- 官方中文文案尽量使用中文，避免不必要的中英文混排。
- 品牌、产品、人名和地名等无稳定中文译名时，保留官方外文名称。

### 8.3 称谓

- 非正式或无明确个体指代时使用「你」，例如文档、博客和群发邮件。
- 指向特定个体且场景较正式时使用「您」，例如个人活动邀请。
- 称呼喜欢产品的人时使用「用户」，不使用「粉丝」。

### 8.4 “应用”相关用词

- 中文产品文案优先使用「应用」或「应用程序」。
- 不把 app 称为「软件」或「程序」。
- 泛指时可写 `app`，句首或标题中可写 `App`。
- `App Store` 是固定写法。
- 不写全大写 `APP`。

### 8.5 图片中的文字

- 在线媒介中不要把大段正文做成图片。
- 图片加载可能失败，图片文字也不能自然适配屏幕和分辨率。
- 各级标题应尽量使用真实文本。
- Logo 等必须使用特殊字体的少量文字可以例外。

## 9. 中文排版规范

### 9.1 空格

- 中文与阿拉伯数字之间加一个半角空格。
  - 正确：苹果公司在 2019 年发布新品。
  - 错误：苹果公司在2019年发布新品。
- 中文与英文之间加一个半角空格。
  - 正确：使用 SDK 开发应用。
  - 错误：使用SDK开发应用。
- 中文标点与相邻字符之间不加空格。
  - 正确：性能提升了 25%，效果明显。
  - 错误：性能提升了 25%， 效果明显。
- 超链接前后建议留一个空格，但原文说明该规则尚有争议；同一产品应统一处理。
  - 推荐：前往 [帮助中心](https://example.com/help) 了解详情。
- 当前后均为中文且不影响准确性时，可优先使用中文数词。
  - 推荐：我们发布了五个产品。

### 9.2 标点

- 中文句子使用全角中文标点。
- 引号只在引用或明确语义需要时使用，不用来装饰普通词语。括号保留出处、定义、单位等必要信息，避免多层插入打断正文。
- 引号样式服从用户体例或既有文档，全文一致。无指定时，本规范采用外层 `「」`、内层 `『』`；不机械替换引文、代码和数学语法。
- 不重复堆叠标点。
  - 可接受：她竟然对你说「喵」？！
  - 不接受：她竟然对你说「喵」？！？！？！
- 省略号使用六点、占两个汉字空间：`……`
- 破折号使用占两个汉字空间的形式：`——`
- 不建议大量使用感叹号或波浪号表达强烈情绪。

### 9.3 三角符

- `▲` 可居中放在照片下方、注释内容前，起指示作用。
- `▼` 可单独居中成行，用于分隔两部分内容或引出下文。
- 三角符属于特定编辑表达，不应替代常规按钮、展开图标或无障碍标签。

### 9.4 段落

- 网页和移动端正文首行不缩进。
- 段落之间使用一个空行或等价的段间距。
- 不在段落开头手动输入空格。
- 富文本中使用样式控制段距，不使用多个空段落堆叠间距。

### 9.5 对齐

- 说明性长文优先左对齐；独立公式按下节在正文区域水平居中。已有正式模板按模板处理。
- 娱乐、浅阅读类内容可使用居中对齐，但应用界面中应谨慎。
- 居中排版宜一句一行、单行较短，且不要混用多种对齐方式。

### 9.6 公式与强调

公式输入、各媒介的渲染方式和检查要求见[格式与保真指导](../../refine-text/references/document-writing.md)。独立公式居中；公式居中不能通过空格、制表符或将整段正文居中实现。

### 9.7 行首与行尾禁则

- 顿号、逗号、句号等点号，以及结束引号、结束括号，不应出现在一行开头。
- 开始引号、开始括号、开始双书名号，不应出现在一行结尾。
- 实现时优先依赖成熟排版引擎的 CJK 换行规则，不手动插入空格修正。

## 10. 西文排版规范

### 10.1 空格

- 数字与普通单位之间加一个半角空格。
  - `10 Gbps`
  - `20 TB`
  - `5 GB`
- 度数和百分号与数字之间不加空格。
  - `233°`
  - `15%`
- 货币符号、正负号与数字之间不加空格。
  - `$10`
  - `-23`
- 逗号、句号、问号、感叹号等点号后加一个空格。
  - `Hello everyone! Welcome to my blog.`
- `@`、`©` 等作为独立标志使用时，其后加空格；电子邮件地址例外。
  - `@ Example`
  - `© Example`
  - `name@example.com`
- 括号和引号内部首尾不加空格；与前后英文正文之间按句法留空格。
  - `5.04 ounces (143 grams)`
- 运算符前后加一个空格。
  - `20 ± 2%`
  - `p < 0.01`
  - `1 + 1 = 2`
- 表示并列选择的斜线前后加一个空格。
  - `开 / 关`
- URL、文件路径、日期、单位组合和官方专名中的斜线不套用上述规则。

### 10.2 数字与字符

- 数字使用半角字符。
- 数字应使用与西文匹配的字体。
- 海报中只有极少量数字、且为了严格对齐时，可谨慎使用全角数字；常规正文和界面不建议使用。

### 10.3 连字符与连接号

- 连字符 `-` 用于组成复合词或连接相关姓名。
  - `Multi-Touch`
  - `Jean-Jacques Rousseau`
- 连接号或破折号用于句中中断、转折或说明；应与普通连字符区分。

### 10.4 斜体

斜体可用于：

- 强调某个词或句子
- 标记外来语或读者不熟悉的词
- 书名、剧名和美术作品名

斜体不应大面积用于正文，也不应作为唯一的状态区分方式。

### 10.5 大小写

- 英文句首字母大写，单词之间留空格。
- 专有名词使用官方规定的大小写。
- 短标题或口号可使用全大写，但需权衡可读性。
- 长正文和复杂标签不使用全大写。

---

## 11. 中西文混排规范

### 11.1 空格

- 中文与英文之间加一个半角空格。
  - `苹果公司发布了 iPhone。`
- 中文与阿拉伯数字之间加一个半角空格。
  - `今天是 2020 年的第一天。`
- 英文或数字紧邻中文全角标点时，不加额外空格。
  - `刚买了一部 iPhone，性能提升了 25%，体验更好。`
- `%`、`°` 等角标式单位符号与数字之间不加空格。
- 品牌或技术名词内部是否加空格，以官方写法为准。
  - `4K`
  - `1080p`
  - `iPhone XS Max`

### 11.2 标点

- 中文主句使用全角中文标点。
  - `核磁共振成像（NMRI）是什么原理？`
- 中文句子中嵌入完整英文句子时，英文句子内部使用半角英文标点。
  - `那句话是「Stay hungry, stay foolish.」`
- 中文标点与相邻英文、数字之间不加空格。
- 不在同一个语义单元中无规则混用全角与半角标点。

### 11.3 字体

- 中文使用中文字体，英文和数字使用匹配的西文字体。
- 混排时应检查基线、字面大小、字重和行高是否协调。
- 同一层级不得因复制来源不同而出现字体和字号漂移。

---

## 12. 专有名词规范

### 12.1 总则

- 品牌名称以官方网站写法为准。
- 应用名称遵循 Google Play、App Store 或产品官方渠道的命名。
- 有官方中文名时使用官方中文名。
- 无官方中文名时，可使用广泛接受的通用译名；否则保留外文，不自行翻译。
- 一般情况下，品牌和应用名称不加直角引号。
- 应用名称过长时，可首次出现时定义缩写，并明确标注“下同”。
- 不使用不地道或团队自造的英文缩写。

### 12.2 常见正确写法

| 推荐写法 | 避免写法 |
|---|---|
| App、app | APP |
| apps | APPs |
| App Store | Appstore、AppStore |
| email | E-mail、Email |
| GitHub | Github、github |
| Google | google |
| iOS | IOS |
| iPhone XS Max | iphone xs MAX |
| kg | KG、Kg |
| km | KM、Km |
| Markdown | MarkDown |
| P.S. | PS、ps、Ps. |
| Siri | siri |
| WeChat | Wechat、wechat |
| WhatsApp | Whatsapp、whatsapp |
| Wi-Fi | WIFI、WiFi、wifi |
| 登录 | 登陆 |

### 12.3 技术名词

- 使用 `JavaScript`，不写 `Js`。
- 使用 `HTML5`，不写 `h5`。
- 使用 `iOS 10`、`macOS`、`Android`、`iPhone` 等官方形式。
- 技术名词与版本号之间是否加空格，以官方写法为先；无明确官方规范时按本文混排规则处理。

---

## 13. 时间、日期、范围、电话与列表

### 13.1 时间

- 使用两位分钟和半角冒号：`12:08`
- 不写：`12:8`、`12：8`

### 13.2 日期

推荐：

- `2020-01-01`
- `2020.01.01`
- `2020 年 1 月 1 日`
- 庄重文字场景可写：`二零二零年一月一日`

避免：

- `2020-1-1`
- `2020年01月01日`

同一产品应选定一种主要日期格式并保持一致。

### 13.3 农历月日

- 使用中文数词：
  - `腊月二十三`
  - `八月十五中秋节`
- 不写：
  - `腊月23`
  - `8月15中秋节`

### 13.4 数值范围

- 范围两端保留单位：
  - `1 天至 560 天`
  - `1 天 ~ 560 天`
  - `5% ~ 10%`
- 不写：
  - `1-560 天`
  - `5~10%`
- 尺寸是特殊情况，单位可统一放在末尾：
  - `10 × 15 × 20 mm`

### 13.5 电话号码

- 长电话号码可按便于识别和拨号的方式分组：
  - `123 4567 8901`
- 不建议连续写成：
  - `12345678901`

### 13.6 有序列表

- 使用 `1.` 形式时，小数点后加一个空格：
  - `1. 静音`
- 使用 `1、` 形式时，顿号后不加空格：
  - `1、静音`

### 13.7 项目列表标点

- 短语式、并列式列表项句末不加分号或句号。
- 完整句、包含内部标点的长句或需要独立阅读的列表项，句末加句号。
- 同一列表应使用同一种句法和标点策略。

---

## 14. 引用规范

- 正文中部分引用第三方内容时，应使用明确的引用样式并给出作者或出处。
- 全篇转载时，应在全文开头显著注明来源并链接原文。
- 不支持超链接时，直接给出文本链接。
- 链接过长且影响版面时可使用可靠的短链接服务，但应确保长期可访问。
- 引用格式应与正文有明显区分，不得让读者误认为原创内容。

## 15. 设计职能与协作边界

| 职能 | 主要职责 |
|---|---|
| 视觉设计—品牌方向 | Logo、品牌识别与第一印象 |
| 视觉设计—运营方向 | 活动视觉、Banner、宣传物料和整体视觉风格 |
| 多媒体设计 | 开场视频、VCR、过渡动画等多媒体内容 |
| UI 设计 | 界面、排版、控件样式和视觉呈现 |
| 交互设计 | 功能结构、跳转、反馈、场景与使用体验 |
| 动效设计 | 弹窗、页面过渡、转场和连续交互动效 |
| 用户研究 | 用户需求、访谈、满意度与研究洞察 |

协作时应先明确问题属于品牌、运营、UI、交互、动效、媒体或研究中的哪一层，再确定负责人和交付物；跨职能问题应共同评审，不以视觉完成替代交互验证，也不以功能可用替代文案和排版检查。

## 16. 规则冲突与统一执行口径

### 16.1 列表项是否加句号

“完整句列表项加句号”与“短项目列表项不加标点”表面上存在冲突。

统一口径：

- 短语、词组、短动作列表：不加句号。
- 完整句、解释性长句、含多个分句的列表：加句号。
- 同一列表保持一致。

### 16.2 数字与单位是否加空格

通则是数字与单位之间加空格；例外是 `%`、`°` 以及官方固定形式。

统一口径：

- `5 GB`、`10 Gbps`、`20 TB`
- `15%`、`233°`
- `4K`、`1080p`
- 品牌与产品型号以官方写法为准。

### 16.3 App、app 与“应用”

统一口径：

- 中文官方文案优先写「应用」或「应用程序」。
- 英文泛指写 `app`。
- 句首、标题或固定名称中按规则写 `App`。
- 固定名称写 `App Store`。
- 不写 `APP`。

### 16.4 超链接前后空格

原文明确说明存在争议。

统一口径：

- 作为中文句中独立可点击文本时，建议链接前后加空格。
- 紧邻中文标点时，标点前不增加额外空格。
- 产品内应选择一种策略并通过组件统一，而不是人工随意处理。

### 16.5 斜线前后空格

斜线空格规则适用于并列和选择关系。

统一口径：

- UI 选择或并列：`开 / 关`
- URL、路径、日期、单位、代码和官方名称：按其自身语法，不加额外空格。

## 17. 交付前检查清单

### 17.1 结构与视觉

- [ ] 所有元素有明确对齐依据
- [ ] 组内间距小于组间间距
- [ ] 页面重点一眼可辨
- [ ] 对比没有错误强调次要信息
- [ ] 同类组件、状态和交互保持一致
- [ ] 页面间颜色、字体、间距和图片风格一致
- [ ] 暖色、冷色和强调色的角色明确
- [ ] 字体数量克制，组合有清晰层级
- [ ] 长正文未使用花体、手写体或全大写

### 17.2 交互与体验

- [ ] 操作后有及时、对应的反馈
- [ ] 文案使用用户语言而非系统术语
- [ ] 高风险错误已优先通过设计预防
- [ ] 选项和动作可见，用户无需反复记忆
- [ ] 关键流程已剔除无关信息
- [ ] 错误信息说明问题、影响和恢复方式
- [ ] 帮助内容按“无需提示 → 一次性 → 常驻 → 文档”选择

### 17.3 中文与混排

- [ ] 中文与英文之间有一个半角空格
- [ ] 中文与阿拉伯数字之间有一个半角空格
- [ ] 中文标点前后无多余空格
- [ ] 中文主句使用全角标点
- [ ] 完整英文句内部使用半角标点
- [ ] 引号有必要且符合所选体例，未误改引用、代码或公式
- [ ] 省略号为 `……`，破折号为 `——`
- [ ] 段首无手工空格，段间距由样式控制
- [ ] 行首行尾标点符合中文换行规则

### 17.4 西文与数字

- [ ] 普通数字与单位之间有空格
- [ ] `%`、`°` 与数字之间无空格
- [ ] 货币符号、正负号与数字之间无空格
- [ ] 英文标点后有一个空格
- [ ] 运算符前后有一个空格
- [ ] 数字和标点使用半角字符
- [ ] 专有名词大小写与官方写法一致
- [ ] 未将 app 写成 APP

### 17.5 文案与内容

- [ ] 无错别字和故意谐音错字
- [ ] 已删除无意义的冗词和重复句
- [ ] “你 / 您”符合对象与场景
- [ ] 使用“用户”而非“粉丝”
- [ ] 中文场景优先使用“应用”
- [ ] 大段正文未放入图片
- [ ] 引用和转载已标注来源
- [ ] 日期、时间、电话和列表格式统一
- [ ] 论文及专业文本的语言润色已使用 academic-humanizer，受影响的数字、公式、引用和呈现已核对
- [ ] 重点加粗克制，独立公式居中，适用的最终渲染已实际检查

## 18. 尚未覆盖、后续需补充的规范
