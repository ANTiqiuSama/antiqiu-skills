# 通用项目 LLM Wiki 迁移教程

> 适用于代码仓库、文档型项目、数据项目、研究项目和多仓协作项目。本文只使用通用占位符，不包含任何具体项目名称、内部仓库地址、人员信息或业务数据。

## 1. 一句话理解

LLM Wiki 是一套“先整理、后查询”的知识工程方法：

- 先让 Agent 阅读代码、设计文档、接口契约、决策记录和运维资料。
- 把重复、分散的原始信息蒸馏成短小、可链接、可溯源的 Markdown 页面。
- 查询时先看索引和摘要，再按需读取正文，只有细节不足时才回到原始资料。

它不是代码搜索、调用图或聊天记忆的替代品。更合理的组合是：

```text
Wiki：提供稳定的项目认知、业务背景和跨文档结论
代码搜索 / LSP：提供精确符号、调用关系和最新实现
RAG / 全文检索：提供长尾资料召回
原始文件：提供最终证据和细节兜底
```

核心原则可以概括为：

1. Compile, don't repeatedly retrieve：把高频知识预先编译成 Wiki。
2. Accumulate, don't rediscover：让每次理解成为下一次工作的基础。
3. Wiki first, source backed：先读 Wiki，但重要结论必须能回到原始来源。

## 2. 什么时候值得迁移

满足以下三项以上时，通常值得建设：

- 项目资料分散在代码、文档、接口契约、Issue、PR 或会议记录中。
- 新成员或新 Agent 经常重复询问相同问题。
- 单次任务需要综合多个模块、多个仓库或多个平台的信息。
- Agent 启动时需要读取大量固定背景资料。
- 关键决策的“为什么”比单纯的代码实现更重要。
- 同一业务概念在客户端、服务端、数据或基础设施中都有不同实现。
- 团队需要可审计、可版本控制、可增量更新的知识产物。

以下情况不宜把 Wiki 当作主方案：

- 项目很小，直接阅读少量文件已经足够。
- 需求是精确的函数调用图或符号跳转，应优先使用 LSP、AST 或代码图谱。
- 信息变化极快，且没有自动刷新或人工复核机制。
- 目标是保存全部对话和个人记忆，应使用专门的记忆系统。
- 数据包含敏感信息，但团队尚未建立权限、脱敏和审计规则。

## 3. 通用知识结构

为兼容原始框架，默认保留三类知识。分类依据是“页面回答什么问题”，而不是编程语言、组织架构或仓库名称。

| 分类 | 回答的问题 | 通用例子 |
|-|-|-|
| `concepts/` | 怎么工作、遵守什么流程或约束 | 请求生命周期、缓存失效、发布流程、错误恢复 |
| `entities/` | 它是什么、负责什么、接口是什么 | 服务、组件、数据库、数据集、外部依赖、角色 |
| `synthesis/` | 为什么这样选、有哪些取舍 | 技术选型、架构决策、方案比较、事故复盘结论 |

推荐目录：

```text
<PROJECT_ROOT>/
├── .config/
│   └── wiki.json
├── wiki/
│   ├── index.md
│   ├── concepts/
│   ├── entities/
│   ├── synthesis/
│   ├── _meta/
│   │   └── taxonomy.md
│   ├── .manifest.json
│   └── log.md
└── AGENTS.md / CLAUDE.md / 其他 Agent 启动文件
```

如果项目包含多个领域或平台，在三类目录下继续分组，不要另外发明一套互不兼容的顶层分类：

```text
wiki/
├── concepts/
│   ├── domain-a/
│   ├── domain-b/
│   └── shared/
├── entities/
│   ├── domain-a/
│   ├── domain-b/
│   └── shared/
└── synthesis/
    ├── architecture/
    ├── product/
    └── operations/
```

## 4. 迁移前的四个门槛

### 4.1 明确读者和用途

至少写出 10 个真实问题，例如：

- 这个项目解决什么问题？
- 核心模块如何协作？
- 一次请求或任务从哪里进入，经过哪些阶段？
- 哪些数据是事实来源？
- 为什么选择当前方案？
- 失败时怎样恢复？
- 新增一个功能通常需要修改哪些区域？
- 哪些约束不能破坏？
- 哪些内容经常被误解？
- 哪些信息必须回到原始代码确认？

这些问题将成为迁移后的验收题，不要只用“生成了多少页”衡量成功。

### 4.2 指定负责人

至少确定：

- Wiki owner：决定范围、结构和发布标准。
- Domain reviewer：确认关键业务与架构结论。
- Security reviewer：确认敏感信息处理方式。
- Maintenance owner：决定刷新频率和过期策略。

第一批页面决定后续结构，建议由同时理解项目和 Agent 工作方式的人审核。

### 4.3 确定安全边界

禁止摄入或输出：

- 密钥、令牌、证书、密码和连接串。
- 真实用户数据、支付信息、联系方式和身份标识。
- 未授权的客户材料、合同或受限文档。
- 未脱敏的生产日志、数据库导出和故障样本。
- 带临时授权参数的内部下载链接。

公开或跨团队分享前，把具体信息替换为稳定占位符：

| 原始类型 | 通用占位符 |
|-|-|
| 项目或产品名称 | `<PROJECT_NAME>` |
| 仓库地址 | `<REPOSITORY_URL>` |
| 人员姓名 | `<ROLE_OR_OWNER>` |
| 内部服务名 | `<SERVICE_A>` |
| 数据表或数据集 | `<DATASET_A>` |
| 内部域名 | `<INTERNAL_ENDPOINT>` |
| 客户或用户 | `<CUSTOMER_A>` / `<USER_A>` |
| 密钥或令牌 | `<REDACTED_SECRET>` |

不要对占位符做可逆映射，也不要把映射表放进可分享的 Wiki。

### 4.4 确定事实优先级

来源冲突时，建议按以下顺序判断：

1. 当前代码、测试、Schema 和正式接口契约。
2. 已批准的 ADR、RFC、设计文档和运行手册。
3. 正式发布记录、Issue 和已合并 PR。
4. 会议纪要、周报和讨论记录。
5. Agent 推断。

无法解决的冲突不要静默选择一方。记录双方来源，标记 `ambiguous`，并列出待确认问题。

## 5. 完整迁移流程

### 阶段 0：建立基线

迁移前保存：

- 10～30个验收问题。
- 当前回答这些问题所需的文件数和大致 tokens。
- 人工认可的参考答案或要点。
- 当前 Agent 启动文件的备份。
- 当前代码提交或资料版本。

这让团队能判断 Wiki 是否真的节省成本、提高覆盖率，而不是只增加文件数量。

### 阶段 1：盘点资料

推荐优先级：

1. 项目入口文档、架构说明和术语表。
2. ADR、RFC、Specs、接口契约和数据 Schema。
3. 核心代码、测试、配置和迁移脚本。
4. 发布流程、运行手册、告警说明和事故复盘。
5. 重要 PR、Issue 和提交历史。
6. 会议记录和聊天摘要，仅作为低置信来源。

默认排除：

```text
.git/
wiki/
node_modules/
vendor/
dist/
build/
coverage/
generated/
tmp/
cache/
二进制和大型媒体文件
锁文件和纯机器生成文件
包含秘密或用户数据的文件
```

不要默认摄入整个仓库。先选择能回答验收问题的最小资料集。

### 阶段 2：创建配置

示例：

```json
{
  "version": 1,
  "name": "<PROJECT_NAME> Knowledge Base",
  "sources": [
    {
      "path": "docs/",
      "exclude": ["wiki/", "generated/", "secrets/"]
    },
    {
      "path": "src/core/",
      "exclude": ["**/*.generated.*", "**/fixtures/private/**"]
    },
    {
      "path": "specs/"
    }
  ],
  "output": "./wiki/",
  "max_pages_per_ingest": 30
}
```

关键要求：

- `output` 必须从 `sources` 中排除，防止 Wiki 把自己再次摄入。
- 先小批量运行，确认质量后再扩大范围。
- 多仓项目应保存来源仓库、相对路径和版本标识，不复制无关仓库内容。
- 绝对路径只适合本机执行；可共享配置优先使用相对路径。

### 阶段 3：设计术语和导航

创建 `_meta/taxonomy.md`，先定义：

- 10～30个核心领域词。
- 每个词的标准写法、别名和不推荐写法。
- 各领域的入口页。
- 跨领域共享概念。

标签不是越多越好。每页建议最多5个领域标签。文件夹负责粗分类，标签负责跨目录关联，`[[wikilinks]]` 负责表达具体知识关系。

### 阶段 4：试点摄入

先选一个范围可控但足够重要的主题，生成5～15页。

每页只回答一个主要问题，并满足：

- 标题能独立说明主题。
- 摘要不超过200字，能够帮助 Agent 判断是否需要读正文。
- 重要事实能追溯到仓库相对路径或稳定文档标识。
- 推断内容使用 `^[inferred]`。
- 存疑内容使用 `^[ambiguous]`。
- 不复制大段原文，不重复其他页面已有内容。
- 至少链接一个上游、下游或相关页面；确实独立的页面需说明原因。

### 阶段 5：页面模板

兼容原始框架的基础 frontmatter：

```yaml
---
title: "<PAGE_TITLE>"
category: "concepts"
tags:
  - "<DOMAIN_TAG>"
aliases:
  - "<ALIAS>"
sources:
  - "<REPOSITORY_RELATIVE_PATH>#<SYMBOL_OR_SECTION>"
summary: "<不超过 200 字的页面预览>"
provenance:
  extracted: 0.80
  inferred: 0.15
  ambiguous: 0.05
created: "YYYY-MM-DDTHH:MM:SSZ"
updated: "YYYY-MM-DDTHH:MM:SSZ"
---
```

可选治理字段：

```yaml
owner: "<ROLE_OR_TEAM>"
status: "draft" # draft | reviewed | verified | deprecated
reviewed_at: "YYYY-MM-DDTHH:MM:SSZ"
review_by: "YYYY-MM-DDTHH:MM:SSZ"
sensitivity: "internal" # public | internal | restricted
```

推荐正文结构：

```markdown
# <PAGE_TITLE>

## 摘要

一句话说明这页解决什么认知问题。

## 范围与边界

说明适用范围、不适用范围和前置条件。

## 工作方式 / 定义 / 决策

解释核心知识；机制页写流程，实体页写职责和接口，综合页写方案与取舍。

## 失败模式与例外

记录常见误解、边界条件、降级和恢复方式。

## 相关页面

- [[<RELATED_PAGE_A>]]
- [[<RELATED_PAGE_B>]]

## 来源

- `<REPOSITORY_RELATIVE_PATH>#<SYMBOL_OR_SECTION>`
```

`provenance` 是来源构成提示，不是经过校准的正确率。不要把 `0.9` 宣传成“90%一定正确”。

### 阶段 6：增量摄入

为每个源文件记录：

- 内容 hash。
- 摄入时间。
- 源文件版本或提交。
- 创建、更新和可能失效的页面。

默认只处理新增和变更源。以下情况再进行全量重建：

- 分类体系发生重大变化。
- 大量页面与当前代码不一致。
- Manifest 损坏或无法确认增量边界。
- 多次局部修复的成本已高于重建。

删除源文件时，不要立刻删除所有相关页面。先检查页面是否还有其他来源；没有来源的页面标记为待废弃或孤儿页，再由负责人确认。

### 阶段 7：创建索引

`wiki/index.md` 是唯一聚合入口，至少包含：

- 项目一句话介绍。
- 核心领域与入口页。
- 关键机制、核心实体和主要决策。
- 常见任务到起始页面的映射。
- “Wiki 不足时去哪里查原始资料”的说明。
- 最近更新时间和健康状态。

索引不是页面全文拼接。它只负责导航和筛选。

### 阶段 8：迁移 Agent 启动段

只有试点验收通过后，才修改 `AGENTS.md`、`CLAUDE.md` 或其他 Agent 启动文件。

使用可重复执行的边界标记：

```markdown
<!-- project-wiki:begin version="1" -->
## Wiki-first startup

1. 先读取 `wiki/index.md`。
2. 根据当前任务读取最多 2～5 个相关页面。
3. 需要精确实现、最新状态或证据时，回到页面 `sources` 指向的原始文件。
4. 不把 Wiki 当作唯一事实来源；发现冲突时以当前代码、测试和正式契约为准。
5. 修改源资料后，提醒更新对应 Wiki 页面和 manifest。
<!-- project-wiki:end -->
```

只修改标记区间，保留文件其他内容。迁移前保存备份或依赖 Git 版本控制，确保能够回滚。

### 阶段 9：验收

最低结构检查：

- 所有页面都有必填 frontmatter。
- `provenance` 三项之和为1。
- 没有断链。
- 没有 Wiki 自我摄入。
- 没有秘密、个人信息和未授权数据。
- 所有重要结论有来源，或明确标记为推断、存疑。
- 没有同一概念的重复页面和不一致别名。

内容验收：

- 用阶段0的问题进行盲测。
- 比较 Wiki 路径与原始资料路径的正确率、覆盖率和 tokens。
- 抽查至少一个简单事实题、一个跨模块题、一个决策题和一个最新实现题。
- 对错误答案定位是摘要、正文、来源、链接还是过期问题。

建议指标，不应机械当作硬标准：

| 指标 | 建议观察方式 |
|-|-|
| 验收问题覆盖率 | 高优先级问题应接近100% |
| 重要结论可溯源率 | 应为100% |
| 断链数量 | 应为0 |
| 非预期孤儿页 | 应接近0 |
| 敏感信息泄漏 | 必须为0 |
| 页面重复率 | 持续下降 |
| 查询 tokens | 相比基线下降，且不牺牲正确率 |
| 新鲜度 | 满足项目定义的刷新 SLA |

### 阶段 10：发布与维护

建议节奏：

- 每次重要架构或业务变更后：增量摄入相关资料。
- 每周或每个迭代：检查新增、修改、删除和未摄入来源。
- 每月或每季度：运行链接、标签、过期和 provenance 审计。
- 重大重构前：保存 Wiki 快照。
- 重大重构后：重新运行基线问题，必要时全量重建。

多人同时维护时：

- `log.md` 按时间合并。
- `index.md` 按页面标识合并并去重。
- `.manifest.json` 按来源键深度合并。
- 内容页必须语义合并，不能简单选一边覆盖另一边。
- 发现“同概念不同文件名”时合并页面并保留重定向或别名。

## 6. 通用查询方法

查询时按以下顺序控制 context：

1. 读取 `wiki/index.md`。
2. 根据标题、标签和摘要选择候选页。
3. 优先选择来源清晰、更新时间新、`extracted` 占比高的页面。
4. 只读取回答问题所需的正文。
5. 沿 `[[wikilinks]]` 补充上下游关系。
6. 需要精确实现、最新状态或高风险结论时，打开 `sources` 指向的原始文件验证。
7. 回答时区分事实、推断和未解决问题。

快速问题可以在索引和摘要层结束；复杂问题再逐层深入。

## 7. 常见失败方式

### 把文件数量当目标

“至少生成300页”容易制造大量薄页和重复页。更好的目标是覆盖高价值问题，并通过查询测试。

### 一次摄入整个仓库

这会吸收生成代码、依赖、测试夹具和秘密。先做资料盘点，再分批扩展。

### 只有总结，没有来源

无法回到证据的 Wiki 会迅速变成新的陈旧文档。

### 把推断写成事实

Agent 可以补全逻辑，但必须用 `^[inferred]` 或 `^[ambiguous]` 标记。

### 启动时读取整个 Wiki

Wiki 的价值来自渐进式读取。启动只读索引和少量入口页。

### Wiki 替代代码搜索

Wiki 适合理解“是什么、怎么工作、为什么”，精确实现仍应查看代码、测试和正式契约。

### 没有回滚方案

修改启动文件、分类体系或进行全量重建前，必须保存 Git 提交或快照。

## 8. 脱敏后的原文结论

所给原文最值得保留的结论是：

- Wiki 的关键产物不是界面，而是结构化、可链接、可溯源的文本。
- 最大收益来自多文档综合和重复查询，不一定来自单页阅读。
- `index → summary/frontmatter → body → raw source` 是控制 context 的核心路径。
- 增量摄入、manifest、链接体检和回滚是长期维护的必要条件。
- 生产 Wiki 的 Agent 与消费 Wiki 的 Agent 应解耦，Markdown 可作为中立交换格式。

通用化时应补充的限制是：

- 单一项目的 token 实验只能证明潜力，不能直接证明所有项目都能获得相同倍数。
- 成本下降不能替代答案正确率、时效性、安全性和人工复核。
- Wiki 与 RAG、LSP、代码图谱应互补，而不是强行互相替代。
- LLM 会产生误判和陈旧内容，“维护成本接近零”不应作为上线假设。

## 9. 最小可行迁移清单

- [ ] 定义10～30个验收问题。
- [ ] 指定 Wiki、领域、安全和维护负责人。
- [ ] 确定数据边界和脱敏规则。
- [ ] 盘点来源并排除生成文件、秘密和用户数据。
- [ ] 创建 `.config/wiki.json`。
- [ ] 创建三类目录、术语表和索引骨架。
- [ ] 试点生成5～15页。
- [ ] 人工审核关键结论和来源。
- [ ] 建立 manifest 和增量更新规则。
- [ ] 运行断链、孤儿、重复、过期和敏感信息检查。
- [ ] 用基线问题测试正确率、覆盖率和 tokens。
- [ ] 验收通过后再迁移 Agent 启动段。
- [ ] 保存快照并定义维护节奏。
