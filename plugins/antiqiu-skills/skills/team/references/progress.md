# 进度证据与检查时间

编写或修改项目探针时读取本文件。普通唤醒复用已经确认语义的探针，不每轮重新分析生产代码。

## 选择下一个有行动价值的边界

估算当前可比较阶段、检查点或外部事件，不能把异质阶段混成一个速率。已知剩余工作量时使用近期实测耗时；只有可靠的阶段计划和各阶段数据齐备时才合计项目时间。未知后续阶段保留未知。用户明确的截止时间或故障发现延迟决定检查上下限，不把默认值当作项目保证。

优先顺序是已有完成事件/结构化进度时间，其次是已核实语义的完成文件元数据，最后才是稀疏监控观测。无需为了获得三个点唤醒三次模型：生产端已有三个以上可用点即可在第一次检查估算。不要把提示词猜测、文件大小、GPU 瞬时利用率或无关作业经验当作进度。

## 完成文件的可复用取样

[completion_history.py](../scripts/completion_history.py) 仅枚举文件名与 mtime，不打开内容。适用于已经核实以下语义的串行任务：每个编号对应一个工作单元，完成后才写分片，恢复时不改写旧分片，也没有复制或 touch 导致时间失真。并行任务、批量写盘和非等价工作单元不能直接套用。

```python
samples = completed_file_samples(
    run / "event_statistics", job_id=job_id, phase=phase,
    total=total, completed=completed, execution_id=execution_id,
    started_at=process_started_at, observed_at=now,
    name_pattern=r"(?P<position>\d{4})_.+\.json", position_offset=1,
)
```

`execution_id` 由适配器核实并稳定编码执行身份，例如 boot id、PID 与 start_ticks；不要只用 PID。`started_at` 限制为当前进程启动后的记录，`position_offset=1` 适用于从零开始的文件编号。默认取最近 32 个点，要求当前 completed 对应最后一点，编号连续、时间严格增加。缺目录、文件竞争、缺口、乱序或样本不足返回 None，表示速率未知，不表示作业失败；探针仍返回实际进程和终态。复制过的记录即使看似单调也不能使用。

已有结构化日志可直接提供同一接口，无需先生成完成文件。只读相关尾部/字段，保留研究中禁止读取中间科学分数的边界。

## 估算与失效

至少三个点产生两个正增量：单元耗时 = 时间差 / 完成数量差。最近 32 个生产端点的最短和最长单元耗时构成外推范围，乘以当前剩余数量；生产端最后完成以来的时间从剩余估计中扣除。区间向外按分钟取整。这是近期实测速率的粗略外推，不是统计置信区间或承诺。

脚本只对身份已核实、仍在运行、阶段与单位可比的状态估时。执行实例、阶段、总量变化或进度回退丢弃监控旧历史；可使用新实例自己提供的有效历史。不同来源不拼接，特别是不把完成时间与模型醒来时间相减来估速。生产端最后一点不是当前计数时，改为重新积累监控观测。

生产端样本最慢耗时超过最快的三倍，或最新点的年龄超过最慢耗时的三倍，脚本不给 ETA；这两个阈值是可理解的保守启发式，项目有更准确模型时可以替换。监控观测没有增量时撤销旧 ETA，恢复推进后的时间差包含停滞时间，不能忽略停滞后继续宣称原速度。

## 调度规则

1. 有有效 ETA：`ceil((较快端剩余分钟 / 3) / 5) * 5`，再限制到项目上下限。进度变多、速度变化和进入收尾都会改变下一次间隔。
2. 阶段/执行身份改变，或明确推进但没有足够历史：采用初始间隔，并优先寻找生产端已有记录。
3. 确实没有可用增量/历史：前次间隔翻倍直至上限。此退避仅处理未知信息，不是对项目耗时的预测。
4. 计数满额但尚无明确终态：先在下限处查收尾，若仍无终态再退避。阶段变更后重新计算；计数满额不能宣布成功。

默认下限 15、初始 60、上限 240 分钟，全部由项目策略覆盖；例如现有 V11 使用 30/60/240。上下限约束检查成本与发现延迟，不是固定两小时。脚本输出 `schedule_basis`、`eta_source`、单元耗时范围和样本数供回查，未知原因在 `eta_unavailable_reason` 中。

`proposed_next_check_at` 只是从观测时刻推导的建议。仍须用实际调度工具更新已有计划并回读；不手写 automation 文件，不自建 cron 或循环睡眠规避工具限制。
